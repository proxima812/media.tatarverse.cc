# Ревью PR

Этот скилл - про механику доведения PR до готовности к мержу, не про то,
хороша ли сама карточка (это `starter-card-review`) и не про то, что
обязательно перед завершением задачи (это `starter-validation`). Здесь -
как узнать тип PR и что с ним конкретно сделать.

## Любой PR - сначала

```bash
gh pr view <номер> --json title,body,headRefName,isDraft,files,labels
gh pr diff <номер>
```

- Диф маленький и по делу - без сопутствующих правок не по теме PR.
- Коммиты и PR-описание объясняют «зачем», а не только «что» - см. `starter-code-style`
  про то же требование к самому коду.
- Никаких «е» и длинных тире нигде в дифе - тот же хук `no-yo-dash.mjs`,
  что и для локальных правок, PR он не проверяет автоматически.
- Правка трогает `astro.config.mjs`/`main.config.ts`/`src/config/**` -
  прочитать `starter-architecture` перед тем, как одобрять.
- Правка трогает `.ts` или фронтматтер `.astro` - `starter-typescript`.
- Перед тем как считать PR готовым - пройти `starter-validation`
  (`bun run verify`), если правка достаточно крупная, чтобы это оправдать.

## PR из `draft-card-pr.yml` (черновик карточки)

Узнать по ветке `card-submission/<submissionId>`, заголовку «Черновик
карточки: ...», `isDraft: true`, единственному новому файлу
`src/data/cards/draft-<slug>.md`. Открыт автоматически по метке `draft-card`
на issue с меткой `card-submission` - бот собрал только то, что не требует
суждения, и намеренно оставил PR невалидным (пустые `categories`/`tags`,
`url: "TODO"`), чтобы никто не смержил его как есть по невнимательности.

Порядок:

1. Открыть связанный issue (`Closes #N` в теле PR) - там под спойлером
   лежит сырой JSON всех полей заявки, включая то, что бот не смог
   разобрать (ссылки, которые он не выбирал за человека, вложения).
2. Заполнить то, что бот оставил TODO - `url` (выбрать из ссылок в
   комментарии над полем), `categories`, `tags` (из `taxonomy.ts`,
   не вольным текстом), логотип, если в комментарии есть временная ссылка
   на файл - скачать и положить в `src/assets/images/logo/<id>.png`,
   прописать путь, TODO-комментарии убрать.
3. Проверить `peoples`, если бот его заполнил - маппинг текста варианта
   в id делается по трем словам (Татары/Башкиры/Крымские татары), в
   заявке могло быть что-то, что не совпало дословно.
4. Переименовать файл: `draft-<slug>.md` - в id по конвенции
   (`starter-card-review`: транслитерация названия + суффикс основной
   категории), `git mv`, поправить путь логотипа, если он уже был указан.
5. Пройти сам `starter-card-review` целиком - это теперь обычная новая
   карточка, отличается только тем, откуда взялся черновик.
6. Добавить EN-перевод `src/data/cards-en/<итоговый id>.md` - без него
   `check:i18n` упадет, а бот его не создает (заявка не собирает
   английский текст).
7. `bun run verify` - PR был красным по дизайну до этого шага.
8. Снять статус черновика (`gh pr ready <номер>`) только после того, как
   шаги выше пройдены - не раньше.

Ссылки на вложения в исходном issue могут содержать `accessToken` в query
самой Tally и быть временными - в финальном файле карточки должен остаться
только путь к скачанному и закоммиченному ассету, не сырая ссылка.

## Защита от подделки уже стоит на уровне workflow

`draft-card-pr.yml` собирает PR только из issue, автор которого -
`github-actions[bot]` (то есть issue пришел от `tally-submission.yml`, а не
написан руками кем попало в публичном репозитории). Если видите PR с этой
веткой, но что-то в содержимом выглядит подозрительно - сверьте с логом
GitHub Actions запуска, а не только с текстом issue.
