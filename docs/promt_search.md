# Deep discovery: поиск новых карточек каталога

Роль: Research Lead + OSINT Researcher + Data Engineer.

Задача - глубокое мультиязычное исследование интернета и пополнение
каталога `media.tatarverse.cc` проверенными карточками проектов.

Это не обычный Google search, а deep discovery с graph traversal,
локальными языками, реестрами, соцсетями и мероприятиями.

---

# 0. Главное правило

Не выдумывай данные.

Не добавляй проект ради количества.

Не утверждай, что использовал поисковик, сайт, язык, API или источник,
если фактически доступа к нему не было.

Каждое поле карточки должно опираться на источник, который ты открыл.

# 1. Что уже есть в репозитории

Прежде чем искать, прочитай факты ниже - они уже собраны, перепроверять их
не нужно, но нужно свериться, если код изменился.

## Схема карточки

Источник истины - `src/content.config.ts`, коллекция `cards`:

| Поле | Тип | Обязательно |
|---|---|---|
| `name` | string | да |
| `description` | string, одно предложение | да |
| `facts` | array, ровно 3-4 строки | да |
| `url` | одна валидная ссылка | да |
| `pubDate` | дата добавления в каталог | да |
| `logo` | локальный файл изображения | нет |
| `categories` | массив из `CATEGORY_VALUES`, минимум 1 | да |
| `tags` | массив из `TAG_VALUES`, минимум 1 | да |
| `peoples` | `tatar` / `bashkir` / `crimean-tatar`, минимум 1 | да |

Больше полей нет. В схеме **отсутствуют**: `id` во фронтматтере, `slug`,
`originalName`, `alternativeNames`, `country`, `region`, `city`,
`languages`, `founded`, `status`, `founders`, `organization`, `email`,
`image`, отдельные поля соцсетей и `sources`.

Это означает три жестких следствия:

1. **Одна ссылка на проект.** Telegram, сайт, Instagram, GitHub - выбери
   один первоисточник, где проект живет активнее всего. Остальные площадки
   либо упоминаются в `facts`, либо не попадают в карточку вовсе.
2. **География, язык, год основания и статус не хранятся.** Они нужны тебе
   для research log и отчета, но в данные не идут. Не предлагай расширять
   схему ради них - это отдельное продуктовое решение владельца.
3. **Evidence и source URL живут в research log**, а не в карточке.

## Таксономия

Источник истины - `src/lib/taxonomy.ts`. Значения закрытые, схема уронит
сборку на любом слове вне реестра.

Категории: `channel`, `author`, `media`, `language`, `lessons`, `graphics`,
`community`, `music`.

Тегов около 130 в группах `roles`, `topics`, `formats`,
`language-technologies`, `audiences`, `features`. Полный список читай в
файле, наизусть не подставляй.

Разумный объем - 3-6 тегов. Пятнадцать тегов ломают AND-фильтр.

Для подсказки категорий и тегов есть готовый инструмент на TypeSafe (Jev):

```bash
bun run suggest:card -- --card <id>
```

Он ничего не пишет, только печатает вероятности по закрытым спискам.
Финальное решение - твое.

## Файлы карточки

- Русская карточка: `src/data/cards/<id>.md` - источник истины.
- **Английский перевод обязателен:** `src/data/cards-en/<id>.md` с тем же
  id, только поля `name`, `description`, `facts`. Число и порядок фактов
  совпадают с русским файлом. `scripts/cards-i18n-baseline.json` пуст (`[]`),
  то есть исключений нет: `bun run check:i18n` упадет на карточке без
  перевода.
- Логотип, если есть: `src/assets/images/logo/<id>.png`, во фронтматтере
  относительный путь `../../assets/images/logo/<id>.png`. Нет логотипа -
  карточка рисует монограмму, это нормально.
- id: латиница, нижний регистр, дефисы, транслитерация названия плюс суффикс
  **основной** категории: `agidel-journal-media`, `arhiufa-channel`,
  `aydar-kalimullin-author`.

## Правила текста

- Никаких «е» с двумя точками и никаких длинных тире: только «е» и обычный
  дефис. Хук `scripts/hooks/no-yo-dash.mjs` заблокирует запись файла.
- Третье лицо, без обращения к читателю.
- Нейтрально: без «лучший», «уникальный», «must have». Самоописание проекта
  пересказывается, а не копируется.
- `facts` - проверяемые факты (год, площадка, периодичность, аудитория,
  формат), а не оценки.

Полный чеклист человека - `.agents/skills/starter-card-review/SKILL.md`.
Если чеклист разошелся с кодом, прав код.

## Каталог не только татарский

Схема поддерживает три народа: татары, башкиры, крымские татары.
Крымскотатарский сегмент - второй по величине. Любой research pass, который
ищет только `tatar`, пропускает треть каталога.

Поэтому к каждой стратегии поиска добавляй башкирское и крымскотатарское
измерение: `башҡорт`, `Bashkir`, `qırımtatar`, `Crimean Tatar`,
`Kırım Tatar`, `qırımtatar tili`, и так далее.

# 2. Ограничения среды

Проверь, что тебе реально доступно, и работай только этим.

- Веб-поиск и загрузка страниц: `WebSearch` и `WebFetch`. Отдельных API
  Yandex, Bing и DuckDuckGo здесь нет. Не пиши в отчете, что использовал их.
- Соцсети: Telegram читается через `https://t.me/s/<username>`. Instagram,
  Facebook, VK и TikTok почти всегда закрыты логин-стеной, поэтому
  верифицируй их через кеш поисковика, ссылки с официального сайта или
  упоминания в СМИ - и отмечай в log, что прямой проверки не было.
- GitHub, GitLab, App Store, Google Play, сайты организаций и реестры
  читаются нормально.
- Субагенты: можно запускать параллельные research tracks через `Agent`.
  Если запустить их нельзя - не имитируй, а выполни треки последовательно и
  скажи об этом в отчете.

# 3. Research strategy до начала поиска

Составь карту пробелов:

- какие категории заполнены хорошо, какие почти пусты;
- какие народы недопредставлены;
- какие географии уже покрыты существующими карточками;
- какие форматы отсутствуют (подкасты, приложения, датасеты, музеи, архивы).

Поиск должен закрывать пробелы, а не наращивать самый простой сегмент.

# 5. Дополнительные источники discovery

- **Мероприятия:** Сабантуи, фестивали, форумы, съезды, конференции,
  конкурсы. У каждого смотри организатора, партнеров, спонсоров, спикеров,
  участников, медиапартнеров.
- **Реестры:** реестры НКО, government registries, списки зарегистрированных
  associations, муниципальные и культурные директории, грантовые базы. Это
  главный канал для небольших организаций без SEO.
- **СМИ:** татарские, башкирские, крымскотатарские и региональные медиа,
  интервью, подкасты, архивы. Схема: статья → организация или человек →
  связанные проекты.
- **Разработка:** GitHub и GitLab (словари, клавиатуры, шрифты, корпуса,
  датасеты, OCR, TTS, переводчики, языковые модели), App Store, Google Play,
  Product Hunt. Это прямой источник для категории `language`, где у каталога
  уже сильная база - проверяй дубли особенно внимательно.
- **Wikipedia** - только для discovery, не как единственный источник.

# 7. Транслитерация и дедупликация

Одна организация встречается под многими именами. Ищи оригинальное название,
татарскую кириллицу, латиницу, английскую и русскую транслитерацию,
официальный перевод.

Пример одного проекта, а не пяти: Бөтендөнья татар яшьләре форумы /
Botendonya Tatar Yashlare Forumi / World Forum of Tatar Youth / Всемирный
форум татарской молодежи.

## Проверка на дубль перед каждой записью

```bash
grep -rn "t.me/<username>" src/data/cards/
grep -rni "<часть названия>" src/data/cards/
ls src/data/cards | grep <slug>
```

Сравнивай: имя, альтернативные имена, домен, username в соцсетях, город,
родительскую организацию. Используй нечеткое сопоставление имен.

Отдельно решай, самостоятельный ли это проект или подразделение, филиал,
мероприятие организации либо ее же вторая площадка. Не дроби организацию на
несколько карточек без причины. Локальное отделение годится отдельной
карточкой, только если оно реально работает как самостоятельное сообщество.

# 8. Люди в каталоге

Каталог **допускает** карточки людей: категория `author`, 42 карточки
(`aigiz-kunafin-author`, `aydar-kalimullin-author`). Критерий - у человека
есть публичный проект: канал, блог, авторская работа, на которую ведет `url`.

Личный аккаунт без публичной деятельности по теме карточкой не становится,
но годится как источник discovery.

Музыканты - отдельная коллекция `src/data/artists/` с другой схемой. Не
заводи их в `cards`, категория `music` для них не предназначена.

# 9. Evidence, статус, доверие

Собирай evidence в research log, минимум первичный источник, по возможности
два независимых подтверждения. Приоритет источников: официальный сайт,
официальная соцсеть, государственный реестр, сайт родительской организации,
авторитетное СМИ, университет, организатор мероприятия, каталог.

Каждый URL проверяй: страница существует, относится к нужному проекту, нет
редиректа на чужой проект, домен не парковочный и не истек, аккаунт не
удален, username принадлежит именно этому проекту.

Активность: не считай проект живым только потому, что домен отвечает.
Смотри последние публикации и события. Схема не хранит статус, поэтому
**мертвый проект просто не добавляется**, если только он не имеет
самостоятельной архивной ценности и об этом честно не сказано в `facts`.

Уровень доверия для log: `high` - официальный источник плюс подтверждение;
`medium` - официальная соцсеть или несколько надежных вторичных источников;
`low` - мало информации, старые упоминания, сомнительная идентификация.
`low` не добавляется автоматически: сначала допроверь.

# 10. Research log

Веди рабочий log вне production-данных, например `docs/research/`:

| Project | Country | Language | Track | Sources | Confidence | Duplicate | Added |
|---|---|---|---|---|---|---|---|

Отдельно - отклоненные кандидаты с причиной: duplicate, unrelated,
no evidence, dead, individual person, insufficient information, spam,
wrong entity, duplicate branch, outside catalog scope.

Отдельно - метрика по языкам: запросов, кандидатов, **уникальных находок
именно благодаря этому языку**, добавлено. Последнее важнее остального: оно
показывает реальную ценность мультиязычного поиска.

Отдельно - матрица покрытия **страна x язык x категория**, чтобы видеть
пробелы.

Перед новым проходом сверяйся с log: если запрос, страна или источник уже
отработаны, меняй стратегию, а не повторяй то же самое.

---

# 11. Насыщение

Не заканчивай исследование потому, что найдено N проектов. Для каждой важной
географии иди до насыщения: несколько разных запросов и обходов источников
подряд перестают давать новые качественные сущности. Тогда переходи к
следующей географии, языку или категории.

# 12. Работа батчами

Реалистичный батч - **8-12 карточек**, а не 20-40: на каждую нужны русская
карточка, 3-4 проверенных факта, английский перевод и подбор таксономии.

Цикл батча:

1. discovery;
2. evidence;
3. верификация URL;
4. проверка релевантности;
5. проверка на дубли;
6. нормализация под схему (id, единственный `url`, категории, теги,
   peoples, pubDate);
7. запись `src/data/cards/<id>.md`;
8. запись `src/data/cards-en/<id>.md`;
9. проверки;
10. следующий батч.

После каждого батча убедись, что репозиторий собирается. Ситуация
«много новых записей, но сборка сломана» недопустима.

## Реалистичная цель

Каталог уже содержит 325 карточек, и очевидные проекты в нем есть. Цель в
100-200 новых записей достижима только при снижении планки качества.

Ставь цель по качеству: **столько карточек, сколько прошло верификацию**.
Ориентир одного полноценного прохода - 40-80 новых карточек. Если после
честного исследования их 47 - оставь 47 и покажи в отчете, где насыщение
наступило.

# 13. Проверки

В репозитории **нет** отдельных команд formatter, lint и tests. Не пытайся
их запускать и не пиши о них в отчете.

Реальные команды:

```bash
bun run check        # astro check: схема контента и типы
bun run check:i18n   # у каждой карточки есть EN-перевод
bun run check:seo    # build + валидация SEO
bun run verify       # все три
```

**Запуск проверок - по решению владельца репозитория.** Не гоняй их сам без
просьбы: сначала спроси. То же про деплой - он делается командой
`bun run cf:deploy`, пуш в main деплой не запускает.

Типобезопасность не ослабляй: никаких `any`, `as any`, `@ts-ignore`,
`@ts-expect-error` и правок схемы ради данных. Данные подгоняются под схему,
а не наоборот.

Существующие проверенные записи без причины не переписывай. Нашел в них
реальную ошибку - подтверди, исправь и укажи это отдельно в отчете.

# 14. Финальные проходы

1. Глобальная дедупликация всего датасета: точные и нечеткие совпадения
   имен, одинаковые домены и usernames, переводы и транслитерации одного
   имени, пары родитель-филиал. Особое внимание проектам, найденным на
   разных языках.
2. Повторная проверка всех новых `url`.
3. Проверка, что у каждой новой карточки есть файл в `cards-en/` с тем же
   числом фактов.

# 15. Финальный отчет

- **Found** - всего кандидатов.
- **Added** - реально добавлено карточек.
- **Updated** - исправлено или дополнено существующих записей.
- **Rejected** - сколько и по каким основным причинам.
- **Duplicates** - сколько дублей поймано.
- **Peoples** - распределение новых карточек по `tatar` / `bashkir` /
  `crimean-tatar`.
- **Categories** - распределение по категориям.
- **Geography** - страны, регионы, города (данные из log, не из карточек).
- **Languages** - таблица `язык | запросов | кандидатов | уникальных находок
  | добавлено`, плюс разделение на языки глубокого поиска, вспомогательные,
  попробованные без результата и продуктивные.
- **Sources** - какие типы источников реально использовались.
- **Track contribution** - вклад каждого трека.
- **Validation** - какие команды запускались и с каким результатом; если не
  запускались, так и написать.
- **Remaining gaps** - плохо исследованные страны, языки и категории,
  недоступные источники, направления следующего прохода.

# 16. Definition of Done

- исследование действительно глубокое, а не первая страница выдачи;
- использованы разные стратегии discovery, включая graph traversal,
  мероприятия и реестры;
- мультиязычный поиск выполнен реально;
- покрыты все три народа каталога;
- дедупликация проведена;
- URL проверены;
- данные соответствуют схеме без ослабления типов;
- у каждой новой карточки есть EN-перевод;
- отчет показывает реальный масштаб работы, включая то, что не получилось.
