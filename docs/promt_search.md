Ты работаешь как **Research Lead + OSINT Researcher + Data Engineer**.

Твоя задача - провести глубокое мультиагентное исследование интернета и собрать максимально полный, проверенный и структурированный каталог проектов, относящихся к тематике текущего репозитория.

Это не обычный Google search.

Нужен **deep discovery / OSINT-style research** с использованием:

* множества языков;

Главная цель:

**не просто найти первые очевидные проекты, а максимально полно картографировать существующую экосистему.**

# 0. Главное правило

Не выдумывай данные.

Не добавляй проект только ради количества.

Не утверждай, что использовал поисковик, сайт, язык, API, инструмент или источник, если фактически доступа к нему не было.

Если среда не позволяет реально запустить несколько независимых subagents:

* не имитируй их запуск;
* создай 4 независимых research tracks;
* выполняй их стратегии последовательно или параллельно настолько, насколько позволяет среда;
* явно укажи это в финальном отчете.

# 1. Главная задача

Найди:

**минимум 100 качественных уникальных проектов.**

Целевая величина:

**150-200 проектов.**

Если глубокое исследование даст больше качественных проектов - можно добавить больше 200.

Но:

**качество > количество.**

Если после полноценного исследования найдено только 137 действительно подходящих проектов - оставить 137.

Не создавать искусственные записи ради достижения числа 200.

Для каждого найденного проекта собери максимально возможное количество **подтвержденных данных** и добавь его в существующую структуру проекта.

# 2. Сначала изучи repository

Перед поиском обязательно:

1. Проанализируй текущий репозиторий.
2. Найди, где находятся данные проектов.
3. Найди schema / types / interfaces.
4. Определи обязательные поля.
5. Определи optional fields.
6. Изучи существующие записи.
7. Определи правила slug/id.
8. Определи используемые категории.
9. Определи формат стран / городов / регионов.
10. Определи формат социальных ссылок.
11. Определи правила локализации.
12. Найди существующие validators.
13. Найди команды:

* format;
* lint;
* typecheck;
* tests;
* build.

14. Проверь существующие записи на потенциальные дубли.
15. Сформируй внутреннюю карту существующего dataset.

Существующая schema репозитория является **source of truth**.

Не придумывай новую структуру данных без реальной необходимости.

# 20. Description Quality

Description не должна быть:

* маркетинговой;
* выдуманной;
* слишком общей;
* основанной на предположении.

Описание должно кратко объяснять:

* что это;
* для кого;
* чем занимается;
* где работает.

При недостатке информации лучше сделать более короткое описание, чем додумывать факты.

---

# 21. Evidence

Для каждой потенциальной записи сохраняй evidence.

Минимально:

* primary source;
* secondary source, если доступен.

Старайся получить:

**2 независимых подтверждения.**

Но отсутствие второго источника не является автоматической причиной отбрасывания, если существует очевидный официальный первичный источник.

---

# 22. Source Priority

Используй приоритет:

1. официальный сайт;
2. официальная социальная сеть;
3. государственный / официальный реестр;
4. официальный сайт родительской организации;
5. авторитетное СМИ;
6. университет;
7. event organizer;
8. каталог;
9. сторонние публикации.

Wikipedia можно использовать для discovery.

По возможности не использовать Wikipedia как единственный источник.

---

# 23. URL Verification

Каждый URL проверяй.

Проверь:

* существует ли страница;
* соответствует ли URL нужному проекту;
* не произошел ли redirect на другой проект;
* не является ли домен парковочным;
* не истек ли домен;
* не удален ли аккаунт;
* не заблокирован ли профиль;
* не является ли ссылка spam/scam;
* принадлежит ли social username именно этому проекту.

Если официальный сайт умер, но проект исторически важен:

можно добавить его при наличии достаточного evidence.

---

# 24. Status Detection

Если schema поддерживает status, различай:

* active;
* inactive;
* archived;
* historical;
* unknown.

Не определяй `active` только по существованию домена.

Проверь:

* последние публикации;
* события;
* announcements;
* social activity;
* recent mentions.

---

# 25. Deduplication

Перед добавлением каждой записи сравнивай:

* name;
* originalName;
* alternative names;
* domain;
* Telegram username;
* Instagram username;
* VK;
* Facebook;
* organization;
* city;
* country;
* founders;
* existing dataset.

Используй fuzzy matching для названий.

Примеры:

`Tatar Youth Finland`

и

`Suomen Tataarinuoret`

могут быть одной организацией.

Нельзя создавать две записи, пока не доказано, что это разные проекты.

---

# 26. Parent Organization vs Project

Отдельно проверяй:

является ли найденная сущность:

* самостоятельным проектом;
* подразделением;
* отделением;
* локальным филиалом;
* мероприятием организации;
* социальной страницей той же организации.

Не дроби одну организацию на множество карточек без причины.

Но локальные отделения можно учитывать отдельно, если они реально работают как самостоятельные сообщества и концепция существующего каталога это допускает.

---

# 27. Confidence

Для research log внутренне оценивай:

* `high`
* `medium`
* `low`

### High

Официальный источник + подтверждение.

### Medium

Официальная социальная сеть или несколько надежных вторичных источников.

### Low

Мало информации / старые упоминания / сомнительная идентификация.

`low` записи не добавлять автоматически.

Сначала попытаться дополнительно проверить.

# 28. Research Log

Минимальная структура:

| Project | Country | Language | Agent | Sources | Confidence | Status | Duplicate | Added |
| ------- | ------- | -------- | ----- | ------- | ---------- | ------ | --------- | ----- |

Также сохраняй:

**Rejected candidates**

с причиной:

* duplicate
* unrelated
* no evidence
* dead/no reliable evidence
* individual person
* insufficient information
* spam
* wrong entity
* duplicate branch
* outside catalog scope

Research log не обязательно добавлять в production repository.

# 29. Language Metrics

Для каждого языка отслеживай:

* сколько запросов сделано;
* сколько кандидатов обнаружено;
* сколько **уникальных проектов** обнаружено благодаря этому языку;
* сколько проектов в итоге добавлено.

Особенно важен показатель:

**language → unique projects discovered**

Например:

| Language | Candidates | Unique discoveries | Added |
| -------- | ---------: | -----------------: | ----: |
| TT       |         31 |                 17 |    14 |
| RU       |         82 |                 43 |    39 |
| EN       |         51 |                 26 |    21 |
| FI       |         12 |                  8 |     7 |
| TR       |         30 |                 17 |    13 |

Это позволит понять реальную ценность мультиязычного исследования.

---

# 30. Search Saturation

Не заканчивай исследование только потому, что найдено 100 проектов.

Для каждой важной географии продолжай discovery до saturation.

Признак saturation:

несколько последовательных разных запросов и source traversals практически перестают давать новые качественные сущности.

После этого переходи к следующей географии / языку / категории.

# 35. Работай batches

Не пытайся одним огромным действием добавить 200 записей.

**20-40 проектов.**

Для каждого batch:

1. discovery;
2. evidence;
3. verification;
4. relevance check;
5. duplicate detection;
6. normalization;
7. schema validation;
8. write data;
9. format;
10. typecheck;
11. lint;
12. tests;
13. build;
14. следующая партия.

---

# 36. Не ломай repository

После каждого крупного batch убедись, что проект продолжает работать.

Не допускается ситуация:

`200 новых записей, но repository больше не собирается`.

---

# 37. Type Safety

Сохраняй максимальную типизацию существующего проекта.

Не обходи ошибки через:

* `any`;
* `as any`;
* `@ts-ignore`;
* `@ts-expect-error`

если это не обосновано существующей архитектурой.

Не ослабляй schema только ради новых данных.

Исправляй данные под существующие корректные типы.

# 38. Existing Data

Не перезаписывай существующие проверенные записи без причины.

Если во время research обнаружена ошибка в существующих данных:

* сначала подтвердить ее;
* затем исправить;
* указать это отдельно в итоговом отчете.

# 45. Definition of Done

Работа считается завершенной только когда:

* проведено действительно глубокое исследование;
* использованы разные стратегии discovery;
* выполнен multilingual search;
* исследованы связи между организациями;
* обработаны мероприятия;
* проведена дедупликация;
* источники проверены;
* данные нормализованы;
* repository остается типобезопасным;
* production build проходит;
* финальный отчет показывает реальный масштаб проведенного исследования.

---

# 46. Главное правило исследования

**Не останавливайся после первой сотни поисковых результатов.**

Исследуй:

**страна → язык → запрос → организация → сайт → соцсети → партнеры → мероприятия → участники → связанные организации → новые проекты.**

Затем повторяй цикл.

Главная цель:

**не формально набрать 100-200 карточек, а максимально полно картографировать существующую экосистему проектов и добавить в каталог только реальные, проверенные и релевантные сущности.**
